## 建议的阅读顺序

按"想干什么"分三条路：

### 🅰️ 第一次打开这个仓库，想搞懂它是什么

1. 根 [`README.md`](../README.md) —— 定位、名字、功能清单、**平台约束（决定了整个产品形态）**、怎么跑
2. [`design.md`](design.md) §0–§2 —— 一句话定义 + 探针实测结论 + 产品形态为什么被逼成这样
3. [`design.md`](design.md) §5.3 —— 三条验收指标（哪三条、目标值、口径）

到这一步就够了，不需要读另外两份。

### 🅱️ 要继续开发 / 加功能

1. [`design.md`](design.md) §4 —— 分层原则（`core/` 纯逻辑 vs 设备层）
2. [`plan.md`](plan.md) 的 `## Global Constraints`（**ArkTS 硬约束，违反即编译失败**）
3. [`decisions.md`](decisions.md) 先读 **Ruling 69–84**（最后一段，最新的口径）—— 尤其：
   - **Ruling 77 / 78**：`protoBin` 产物取证的规范（**只看文件大小必然漏判**）
   - **Ruling 79 / 80**：回弹率与决策间隔的口径，以及**为什么一个改了一个有意不改**
   - **Ruling 81**：口径变了，全仓注释必须跟上
4. 再按需回查某个 Task 的细节（`plan.md` 里 `### Task N` 与 `decisions.md` 里 `### Task N` 标题同名，可对读）

### 🅲 想复查某个结论"凭什么"

直接进 [`decisions.md`](decisions.md) 按 Ruling 编号定位（全文检索 `Ruling NN`）。
台账的写法是"**结论 + 推翻它的数据 + 代价**"，不是流水账。

## 「Ruling」是什么

**Ruling = 决策裁决记录。**

执行这份计划时，每遇到一处"计划没写 / 写了但不对 / 两种做法都说得通"的地方，就在台账里立一条 Ruling 编号，
写清三件事：

1. **裁决**：决定怎么做
2. **依据**：凭什么这么定 —— 通常是**实测数据**（真机读数、编译器报错、对照实验），不是偏好
3. **代价**：这个选择的代价是什么、什么情况下要翻案

台账里 **84 条 Ruling**，价值最高的是**结论被推翻的那几条** —— 它们记录的是"我们本来以为 X，数据说是 Y"：

| Ruling | 原结论 | 推翻它的数据 | 结果 |
|---|---|---|---|
| **1** | 包名可以叫 `com.example.photowall` | `.p7b` 调试 profile 与包名绑定，改名即失配 | 包名留在 `com.example.photospike`（**至今仍是占位符**） |
| **74** | 上墙转化率目标 15%–30% | 上墙改成一步直达的按钮后，"上界"衡量的是**已不存在的交互**；且实测读出过 `150%`（分母被分子吃掉） | 上界取消，只判 `≥ 15%`；分母改定为**收藏池** |
| **77 / 78** | 产物"变了没有"看文件大小 + mtime | A/B/C 对照实验：**同源码两次构建字节全同**（构建确定），但**改注释就能让大小相同而哈希不同**；且产物字节**依赖检出路径** | 只看大小**必然漏判**；跨目录比对**无效**；取证要 grep 符号且**先剥注释** |
| **79** | 回弹率分母 = 排除 `wall` 的事件数（`4/24 = 16.67%`） | 真机数据：`none → wall` 显示**回弹就发生在最终上墙的那次尝试里**；回弹后成功滑出是**一次手滑**而非两次尝试 | 分母改为**尝试组数**（`photoId\|shownAt`）→ `4/47 = **8.51%**`（**高于 spec 目标 3%，未达标**） |
| **80** | 中位数也有同样的"一次尝试算多次"缺陷，应当一并修 | 但**排除 `wall` 对中位数是保守的**（会让中位数偏高），与回弹率方向相反 | **有意不修**；实测 `656.5 ms` 是**偏悲观的上界**，达标 |

> 台账的另一半价值是**记录自己的错**：Ruling 76 / 83 / 84 记的是"把检测失败当成事实，从而算出 `NaN%`"
> 这类作业事故，以及"并发 agent 抢同一个工作树"的代价。这些是给下一次的自己看的。
