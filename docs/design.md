# 照片墙（Photo Wall）产品与技术设计

- **日期**：2026-10-08
- **平台**：HarmonyOS 7（API 26）/ ArkTS
- **状态**：设计已通过真机探针验证，待评审
- **代码名**：`PhotoWall`（探针工程为 `PhotoSpike`）

---

## 0. 一句话定义

> 一款把相册变成**可刷的回忆流**和**可挂的地图照片墙**的鸿蒙应用：分批认领照片 → 逐张滑动决策 → 精选照片挂到地图地点上。

---

## 1. 探针验证结论（设计的事实基础）

本项目在写设计之前先做了真机探针（`PhotoSpike`），以下是**实测结论**而非文档推断。每条都改变了设计。

| # | 问题 | 实测结论 | 对设计的影响 |
|---|---|---|---|
| Q1 | 能否枚举整个相册 | ❌ **不能**。声明 `ohos.permission.READ_IMAGEVIDEO` 后装包即失败：`install failed due to grant request permissions failed. PermissionName: ohos.permission.READ_IMAGEVIDEO` | **产品形态的根本约束**，见 §2 |
| Q2 | EXIF GPS 是否可读 | ✅ **可读**。授权 `ohos.permission.MEDIA_LOCATION` 后读到真实坐标 `31.24995, 121.48135` | 地图墙可自动定位 |
| Q3 | 缩略图 | ✅ `PhotoAsset.getThumbnail()` 成功 | 无需自建缩略图缓存 |
| Q4 | 受限权限是否可申请 | ❌ 调试签名下被拒 | 放弃全库路线 |
| Q5 | Picker 批量能力 | ✅ **43 张 / 9.5 秒**；`maxSelectNumber` 上限 500 | 认领粒度可行 |
| Q6 | 能否绕过 medialibrary 读文件 | ✅ **能**。`fileIo.openSync(uri)` → `image.createImageSource(fd)` → `getImageProperties()` 全通，拿到时间 + GPS | **技术底座**：不依赖 medialibrary 读数据 |
| Q7 | URI 是否"永久授权" | ✅ **跨 App 重启成立**（重启后 `1/1` 可读、GPS 仍在） | 认领一次，长期有效 |
| — | GPS 脱敏机制 | `MEDIA_LOCATION` 未授权时系统**主动脱敏**抹除 EXIF 位置字段；授权后"脱敏级别变为不进行脱敏" | 该权限是**必需**的，不可省 |

### 1.1 关键推论

1. **产品不需要任何受限权限**——因为读文件走 `fileIo` 而非 medialibrary，`READ_IMAGEVIDEO` 完全绕过。
2. **唯一必需的权限是 `ohos.permission.MEDIA_LOCATION`**（普通权限，`normal` / `user_grant`，面向所有应用开放）。
3. **`MEDIA_LOCATION` 必须与 Picker 配合**——Picker 放宽的是"授权范围"，**不放宽 EXIF 脱敏**。官方对 PhotoViewPicker 的说明明确写了 EXIF 位置会被去隐私化处理。

## 2. 产品形态（受约束后的重新定位）

### 2.1 定位

**「分批认领 + 有限刷 + 地图墙」的个人回忆馆**，而**不是**「刷全部相册的清理工具」。

清理定位退位的原因不是偏好，是**平台限制**：全库枚举需要受限权限，拿不到。因此删除/归档**只对已认领的照片有效**，产品重心必须是"重新看见 + 收藏 + 上墙"。

### 2.2 一个意外的一致

原本"每天有边界、不做无限流"是出于产品判断（相册让人焦虑的根源是"太多了"）。现在平台从技术上强制了"有限"——**两条理由指向同一个设计**。这不是妥协，是收敛。

### 2.3 核心循环

```
首次使用：引导认领一批照片（建议引导选"旅行照"，首屏即有地图墙可看）
   ↓
日常使用：滑动决策 → 收藏 → 精选上墙 → 地图墙成长
   ↓
增量：新照片需要主动"补选"，做成有仪式感的动作而非"同步"
```

### 2.4 已知代价（明示）

- **新拍照片不会自动出现**，需主动补选。设计上把它做成"把这几天的照片挂进来"的仪式，而非同步等待。
- **认领有批次成本**：每批上限 500 张。需设计省力的批量选择引导（按时间、按相册、按旅行事件）。
- **删除范围有限**：只能删已认领的照片。

## 3. 功能范围

### 3.1 首版必做（M1）

| 功能 | 说明 |
|---|---|
| 认领流程 | 系统 Picker 多选 → URI 落盘 → 永久授权 |
| 滑动决策 | 右滑收藏 / 左滑归档 / 点按详情 / 长按菜单（上墙·跳过·删除） |
| 收藏页 | 收藏池，可取消、可进入上墙 |
| 上墙 | 收藏后 4 秒窗口期内浮出按钮（备选：双击，A/B 可切换） |
| 地图照片墙 | 离线中国地图 + 地点钉 + 垂线挂照片 + 自适应聚散 |

### 3.2 M2 及以后

- 相似照片分组（连拍清理）
- 回访机制（3 个月前的收藏重新出现问"还留吗"）
- 世界地图切换（墙上有境外照片时自动解锁）
- 搜索、按时间轴浏览

### 3.3 明确不做（Non-goals）

| 不做 | 原因 |
|---|---|
| 全库扫描/自动发现新照片 | 受限权限拿不到，技术上不可能 |
| 云同步、账号体系 | 首版本地优先；数据层留接口，不写云代码 |
| Android / iOS 版本 | 本设计只覆盖鸿蒙 |
| AI 人脸/场景识别 | 确定性算法足够解决首版问题，且无模型依赖 |
| 社交分享、多人协作 | 与"个人回忆馆"定位冲突 |

## 4. 技术架构

### 4.1 分层原则

**原生 ArkUI 负责跟手性，H5 负责视觉迭代量大的地图**。这个划分来自实测的性能边界。

| 层 | 承担 | 理由 |
|---|---|---|
| **ArkUI 原生** | 滑动卡堆栈、手势、弹簧回弹、触感、决策状态机 | 官方实测 ArkTS↔H5 通信 7–9ms，且 `renderMode` 的 `ASYNC_RENDER` 不可动态调整——**Tinder 式跟手拖拽在 H5 里做不出原生手感** |
| **ArkWeb (H5)** | 地图照片墙、离线 GeoJSON 底图、垂线动效、收藏/归档页 | 地图是性能不敏感但视觉迭代量巨大的部分，H5 里调参快；且这部分代码将来可复用于其他平台 |

**H5 通道（仅在需要时启用）**：`https://local.app/` 自建域名 + `onInterceptRequest` + `setResponseData(fd)` 零拷贝。
- 官方明确「此句柄由系统的 Web 组件负责关闭」
- 异步姿势：`setResponseIsReady(false)` **必须在 return 之前同步调用**，就绪后置 `true`
- **禁止用 base64 传照片**：膨胀 33%，且 TaskPool 序列化有 16MB 上限

### 4.2 代码组织（平台无关核心 / 平台相关外壳）

```
PhotoWall/
├─ entry/src/main/ets/
│   ├─ core/                  ← 纯逻辑，可单测
│   │   ├─ phash.ets          dHash + 汉明距离
│   │   ├─ quality.ets        Laplacian 方差 + 直方图削波（绝不用文件大小）
│   │   ├─ grouping.ets       时间簇 + 相似分组（并查集）
│   │   ├─ geo.ets            地点三级归一、屏幕坐标聚类
│   │   ├─ projection.ets     Region 描述符 + 投影函数
│   │   ├─ queue.ets          卡片队列状态机
│   │   └─ model.ets          数据模型 + 版本迁移
│   ├─ data/                  ← 数据源（可替换）
│   │   ├─ ClaimStore.ets     URI 认领与落盘
│   │   └─ ExifReader.ets     fileIo + ImageSource 读 EXIF
│   ├─ ui/                    ← ArkUI 界面
│   └─ map/                   ← ArkWeb 宿主与通道
└─ assets/geo/                离线边界 GeoJSON
```

**移植账（诚实核算）**：`core/` 约 90% 可逐行翻译（纯函数、无平台概念）；数据模型 100% 复用；地图视觉与交互参数 100% 复用；UI 层与手势层为耗材。

### 4.3 数据模型

```
ClaimedPhoto   { photoId(uri), claimedAt, batchId }
Decision       { photoId, state, decidedAt, deferCount }
                 state ∈ unseen | archived | faved | walled
Pin            { id, name, lat, lon, kind: gps|manual|named, createdAt }
WallItem       { photoId, pinId, hungAt, order, note? }
```

**硬规则**：
- **照片永不复制、永不移动**——所有表只引用 `photoId`
- `Decision.deferCount` 是"跳过"次数的依据（跳过 3 次以上插到队列前面）
- 墙是"引用 + 位置"的关系，摘墙/上墙是无损操作

### 4.4 关键实现约束（实测校准）

以下均为**编译器实测**结果，不是文档推断：

| 约束 | 正确做法 |
|---|---|
| `FetchResult.getFirstObjects()` **不存在** | 用 `getFirstObject()` + 循环 `getNextObject()`（**两者返回 Promise**） |
| `PhotoAsset.open()` **不存在** | 用 `fileIo.openSync(asset.uri, READ_ONLY)` 取 `.fd`，**自己负责 closeSync** |
| `String.fromCharCode.apply` 不可用 | ArkTS 禁 `Function.apply`/`Function.call`，显式循环拼接 |
| `??` 空值合并不可用 | 用 `\|\|` |
| 谓词列名 | 用 `photoAccessHelper.PhotoKeys.URI`，不要写字面量 `'uri'` |
| `FetchResult` 持有数据库连接 | **必须 `close()`**，否则连接池耗尽 |
| 坐标格式 | EXIF 返回 `"31, 14, 59.821472"` 度分秒字符串，需换算；`REF` 可能是 `'N'/'E'` 或 ASCII `'78'/'69'`，**两种都要兼容** |
| API 版本 | `createThumbnail()`（吃内嵌缩略图）与 `readImageMetadata()`（强类型 GPS）需 API 26，**已确认可用**，优先用 |

## 5. 交互设计

### 5.1 手势语义

| 手势 | 状态 | 说明 |
|---|---|---|
| **右滑** | `faved` | 收藏。肌肉记忆与 Tinder/抖音一致 |
| **左滑** | `archived` | 归档（**不是删除**）。从流里退出，照片仍在相册 |
| **上下滑** | 不承载决策 | 垂直方向留给内容浏览与系统语义（刷/刷新） |
| 点按 | 详情 | 不进状态机 |
| 长按 | 菜单 | 上墙 / 跳过 / **真删除** |

**为什么左滑是归档而非删除**：误删代价不可逆会让滑动变犹豫，毁掉手感；且鸿蒙删除虽进回收站（保留 30 天），仍是重决策。归档与删除分离——归档是策划，删除是决断。

### 5.2 上墙

**上墙不是手势，是按钮**。理由：滑动是"本能第一判断"，上墙是"再决定一次是否公开陈列"，认知层级不同。

流程：右滑收藏 → 卡片底部浮出「挂上墙」按钮 → **4 秒窗口期**（不点自然淡出）。
- 窗口期制造"照片还热着"的时机，命中率最高
- 错过也不惩罚，收藏页随时可补
- 备选方案：双击上墙（更快但有误触风险），**原型做成两套可切换对比**

### 5.3 验收指标（可测，不靠感觉）

| 指标 | 目标 | 含义 |
|---|---|---|
| 决策间隔中位数 | < 1.2 秒 | 超过说明手势或按钮位置有问题 |
| 误操作率（滑到一半回弹） | < 3% | 超过说明方向映射不直觉 |
| 上墙转化率（收藏池→上墙） | **≥ 15%**（只判下限） | < 15% 说明上墙入口太弱、用户想不到去挂 |

**上墙转化率的目标已修订（2026-10-10，真机数据驱动）**：

- **原目标 15%–30% 的上界已取消。** 它假设的流程是"先收藏，再从收藏里挑着上墙"（**两步**），
  此时转化率天然低；而**「上墙」现在是四个按钮之一（一步直达）**，上墙本身就是直接动作，
  转化率自然高。**上界衡量的是一种已经不存在的交互**。
- **口径**：分母 = **收藏池**（`faved ∪ walled`），不是 `faved`。因为 `applyDecision('wall')`
  **直接把状态写成 `walled`**，只数 `faved` 会让**分母被分子吃掉**
  （实测会读出 `33/22 = 150%` —— 百分比超过 100% 是"分母选错"的典型症状）。
- **首次实测真值（用户设备，2026-10-10）**：`walled 33 / 收藏池 55 = 60%`。
  这个数**不是缺陷**，是行为事实：能入用户眼的照片本就不多
  （"值得留下"共 55 张 = 全部 239 张的 23%），而**入眼的多半想挂地图上** ——
  这恰好印证本产品的定位「**核心是"重新看见"**」：上墙 = "我想再看见"，而它一步就能做到。

## 6. 地图照片墙

### 6.1 视觉规则

照片**不垂直下垂，沿弧线扇形展开**（垂直线会像鱼线，弧线才像风铃）。垂线从钉的正上方落下，照片挂在末端，线长随张数微调避免遮挡。

### 6.2 自适应聚散（落成明确阈值）

| 条件 | 表现 |
|---|---|
| 可见钉 ≤ 3 | 全部展开，每钉最多 9 张，超出显示 "+N" |
| 4–15 个钉 | 展开张数 ≥ 3 的钉；单张钉只显示钉点 |
| > 15 个钉 | 全部收成钉（带张数角标），点击飞过去并只展开它 |
| 钉间距 < 40pt（屏幕坐标） | 强制合并为一个簇 |
| 缩放 < 阈值 | 忽略展开态，全部按钉渲染 |

**聚类判定用屏幕坐标而非经纬度**——"看起来挤不挤"是屏幕空间属性。

### 6.3 地点三级归一（解决 GPS 抖动与分裂）

同一景区可能产出 8 个坐标点，按原始坐标画钉会很难看。

1. **空间聚类**：阈值约 500 米，钉坐标取簇内**中位数**（对离群点比平均值稳）
2. **地名词典**：**离线**城市/景区词典做最近邻匹配。**不接在线反向地理编码**——避免网络依赖与坐标外泄。宁可名字粗（"杭州市 · 西湖区"）也不发坐标出去
3. **用户覆盖优先**：用户手动指定的名字/位置/合并决定**永久覆盖**算法结果

### 6.4 无 GPS 照片

手动指定地点（"这张挂哪儿？"），从最近地点、附近地点中选，或在地图上拖钉子。
理由：地点不明确的照片问用户，本身就是有情感价值的决策（老家、母校）；且推错会让用户不信任地图。

### 6.5 Region 抽象（换地图=换配置）

```ts
type Region = {
  id: 'china' | 'world' | ...
  name: string
  geojson: string
  projection: 'mercator' | ((lon, lat) => [x, y])
  bounds: [minLon, minLat, maxLon, maxLat]
}
```

**中国地图为首版必需，世界地图为 M2**。世界地图不设切换按钮，而是当墙上有境外照片时**自动解锁**（"你有 3 张照片在墙外，要看看世界地图吗？"）——比一开始给个开关更有惊喜感。

**离线 GeoJSON**：中国省/市边界约 500KB–2MB，零网络依赖、零配额、零隐私问题，且可完全控制视觉风格（回忆馆需要温柔的地图，不是工具感的在线地图）。

## 7. 相似照片分组（M2）

**用确定性算法，不用 AI 识别**——因为确定性算法可在真机上调参验证，无需模型、无网络依赖、不会时好时坏。

1. **时间切段**：按拍摄时间排序，相邻间隔 ≤ 20 秒归入同一时间簇（覆盖绝大多数连拍）
2. **视觉验证**：簇内相邻算 dHash（64 位），汉明距离 ≤ 10 判为相似；主色调直方图二次确认（防"翻页拍文档"误判）
3. **并查集合并**成组，组内按质量分排序
4. **质量分用绝对指标**：Laplacian 方差（清晰度）+ 直方图削波（曝光）。**绝对不用文件大小**——HEIC 与 Live Photo 会让该指标彻底失真

**呈现方式**：不是独立"清理模式"，而是卡片上的角标（"8 张相似"），上推展开成微型滑动流逐张挑。让清理顺手发生，而不是变成第二份工作。

## 8. 队列与状态机

**队列顺序**：主体按时间倒序（今天 → 往回走），穿插两类内容：
- **今日回忆**：几年前"同一天"的照片作为彩蛋
- **回访**：3 个月前的收藏随机抽 1–2 张回来问"还留吗？"

**跳过必须重新入队**，且越跳越靠前（跳过 3 次以上插到前面）。这让"我不确定"成为合法答案——用户不必在"留"与"删"之间二选一，那才是刷相册最累的地方。副产品是"待定"集合本身很有价值（往往是情绪张力最强的照片）。

---

## 9. 隐私

- **所有照片与墙数据留在本地**，首版零上传
- **不做在线反向地理编码**——坐标不出设备
- 唯一权限 `MEDIA_LOCATION` 的 `reason` 文案必须写人话（系统会把原文显示在权限弹窗里，模糊表述会导致用户拒绝）
- 数据层接口化，为将来可能的 iCloud 级同步预留接缝，**但不写云代码、不做账号**

## 10. 风险与未决项

| 风险 | 等级 | 应对 |
|---|---|---|
| 认领批次成本高，用户中途放弃 | 🟠 高 | 引导首批选"旅行照"（首屏即出地图墙，惊喜感最强）；提供按时间/相册/事件的批量选择 |
| 新照片不自动出现导致体验缺口 | 🟠 高 | 做成"把这几天的照片挂进来"的仪式，而非同步等待 |
| 上墙按钮强度不足导致墙长不起来 | 🟡 中 | 4 秒窗口期 + 备选双击方案，A/B 实测（指标见 §5.3） |
| 滑卡手感在 ArkUI 上仍需调优 | 🟡 中 | 垂直手势不承载决策；手写 Pointer Events + 速度阈值 + 弹簧回弹，不引入手势库 |
| 地点名字不够精确 | 🟢 低 | 离线词典 + 用户手动覆盖，接受粗粒度 |
| 鸿蒙后续版本调整权限策略 | 🟡 中 | 数据层接口化；若将来放开全库权限，`ClaimStore` 可替换为直读数据源 |
